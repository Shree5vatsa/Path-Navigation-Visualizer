Path Navigation Visualizer — Technical Interview Study Guide

Every algorithm, every engineering decision, every design pattern — explained at maximum depth for interview rounds. Nothing skipped.

Chapter 1: Project Overview — What Is This and Why Does It Matter?

What You Built

Path Navigation Visualizer is a fully interactive, browser-based algorithm visualization platform built in React + TypeScript (Vite). It lets users visually explore and compare four pathfinding algorithms and two maze generation algorithms on a live 2D grid, with complete interactive wall-drawing and real-time animation speed control.

💡 Elevator Pitch for Interviewers

"I built a real-time pathfinding and maze-generation visualizer in React + TypeScript. The core challenge was building a 60fps animation engine that could display thousands of cell state changes smoothly without blocking the UI thread. I implemented four pathfinding algorithms (BFS, DFS, Dijkstra's, and A*) and two maze generators (Binary Tree and Recursive Division), all with a live speed-control system that lets users change animation speed mid-flight using React refs to bypass re-render latency."

What Makes This Technically Non-Trivial

  • Scale: Default grid is 47×87 = 4,089 cells. A full maze generation or pathfinding run touches every single one.
  • Performance: Animating 4,000+ DOM mutations per second without requestAnimationFrame or batch-rendering would freeze the browser entirely.
  • Live Speed Control: Speed changes must take effect on the very next animation frame, not after the current animation finishes — requiring a React ref pattern to bypass the re-render cycle.
  • Algorithm Correctness: A* requires Manhattan distance heuristics and a two-table f(n) = g(n) + h(n) cost model. Getting wrong grid indices would silently return incorrect paths.
  • Touch + Mouse: Wall-drawing works on both mouse (drag) and touch (mobile swipe) with Bresenham-style linear interpolation to fill gaps from fast swipes.

Feature List

  • 4 pathfinding algorithms: BFS, DFS, Dijkstra's, A*
  • 2 maze generators: Binary Tree (NE-bias), Recursive Division (chamber splitting)
  • Interactive wall drawing (click+drag) and erasing
  • Configurable grid sizes (9×17 Mini up to 65×105 custom)
  • Live mid-animation speed control (Slow / Medium / Fast) with zero stutter
  • Distinct SpeedControl component with animated SVG tachometer gauge
  • Toast notification system for user feedback
  • Responsive layout (mobile + desktop)
  • Color-coded Legend and Author Credits footer

Data Flow: Running a Pathfinding Algorithm

1
User clicks ▶️ Start in Nav.tsx

handlerRunVisualizer() is called. It resets all tile traversal states on the grid, then calls runPathAlgorithm({ algorithm, grid, startTile, endTile, speed: speedRef }).

2
Algorithm runs synchronously

The selected algorithm (e.g. bfs(grid, startTile, endTile)) executes entirely in-memory in milliseconds, building two arrays: traversedTiles[] (search order) and path[] (optimal path found by backtracking).

3
animatePath() streams results

animatePath(traversedTiles, path, startTile, endTile, speed) creates step callbacks (closures) for every tile and passes them to runFrameAnimation(steps, getRate).

4
requestAnimationFrame engine renders

The frame loop fires once per monitor refresh. Each frame computes stepsToAdvance = dt / msPerStep using delta-time accumulation, applies exactly that many DOM mutations (className changes), then schedules the next frame.

5
React state syncs after completion

Only after the full animation Promise resolves does setGrid() sync the DOM-mutated tile states back into React state. This prevents thousands of unnecessary re-renders during animation.

Chapter 3: Core Data Model — The TileType Interface

Every single cell in the grid is represented by a TileType object. Understanding this interface is the key to understanding every algorithm in the project.

export type TileType = {
  row: number;        // 0-indexed row position in the grid
  col: number;        // 0-indexed column position
  isStart: boolean;   // Is this the start node? (fixed at [1, 1] by default)
  isEnd: boolean;     // Is this the goal node? (fixed at [r-2, c-2] by default)
  isWall: boolean;    // Is this tile blocked? (set by user drawing or maze generator)
  distance: number;   // Shortest known distance from start (Infinity until visited)
  parent: TileType | null;  // Pointer to previous tile in optimal path (for backtracking)
  isPath: boolean;    // Is this tile on the final backtracked path?
  isTraversed: boolean; // Has this tile been visited by the algorithm?
};
📌 Why parent is the Key Field

The parent field forms a linked-list backwards from the goal to the start. After any algorithm terminates at the goal, you call path.unshift(curr); curr = curr.parent in a while loop to reconstruct the full optimal path. Without parent, there is no way to trace back the shortest route even if you found the goal.

The Grid Type

export type GridType = TileType[][];  // 2D array: grid[row][col]

Grid dimensions are configurable. The default is 47 rows × 87 columns (odd numbers chosen so maze rooms and corridors align symmetrically). All algorithms operate on mutable references to this same grid object — they do not copy it.

The SpeedType

export type SpeedType = 2 | 1 | 0.5;
// 2   = Slow  (0.5× speed)  — high ms-per-step, slow animation
// 1   = Medium (1.0× speed) — balanced timing
// 0.5 = Fast  (2.0× speed)  — low ms-per-step, rapid animation

This counter-intuitive naming exists because speed originally controlled a sleep interval multiplier: Slow meant waiting 2× longer per step (higher ms), and Fast meant waiting 0.5× as long. The multiplier badges in the SpeedControl component show the inverse (0.5×, 1.0×, 2.0×) to match user mental models ("Fast = 2× speed").

Chapter 4: Pathfinding Algorithms — Deep Dive

All four algorithms follow the same contract: they accept (grid, startTile, endTile), run synchronously, and return { traversedTiles, path }.

BFS — Breadth-First Search

Data structure: Queue (FIFO). In JavaScript, this is implemented as a plain array with .push() to enqueue and .shift() to dequeue.

Core idea: Visit nodes level by level outward from the start. Because all edge weights are 1 (each grid step costs 1), the first time BFS reaches the goal it is guaranteed to have found the shortest path.

// BFS core loop (simplified)
const queue = [startTile];
while (queue.length) {
  const tile = queue.shift();       // FIFO — dequeue from front
  if (tile.isWall) continue;
  if (tile.distance === Infinity) break;  // Unreachable frontier
  tile.isTraversed = true;
  traversedTiles.push(tile);
  if (isEqual(tile, endTile)) break;   // Goal reached!

  for (const neighbour of getUntraversedNeighbours(grid, tile)) {
    if (!isPresentInQueue(neighbour, queue)) {
      neighbour.distance = tile.distance + 1;
      neighbour.parent = tile;          // Link for backtracking
      queue.push(neighbour);
    }
  }
}
✔ Why BFS Always Finds Shortest Path on Unweighted Grids

BFS explores in expanding concentric "rings" from the start. The first time it touches the goal, it has taken the minimum number of steps because it has exhausted all shorter paths first. This guarantee only holds when all edge weights are equal — exactly the case on this grid where every step costs 1.

Time Complexity: O(V + E) where V = grid cells, E = valid edges (≤ 4 per cell).

Space Complexity: O(V) for the queue and visited tracking.

Best for: Shortest path in unweighted graphs. Most visually satisfying wave-front expansion.

DFS — Depth-First Search

Data structure: Stack (LIFO). Implemented with .push() and .pop() on an array.

Core idea: Dive as deep as possible along one path before backtracking. This means DFS often finds a path, but almost never the shortest path.

// DFS core loop (simplified)
const stack = [startTile];
while (stack.length) {
  const tile = stack.pop();    // LIFO — pop from top
  if (tile.isWall) continue;
  tile.isTraversed = true;
  traversedTiles.push(tile);
  if (isEqual(tile, endTile)) break;

  for (const neighbour of getUntraversedNeighbours(grid, tile)) {
    if (!checkStack(neighbour, stack)) {
      neighbour.distance = tile.distance + 1;
      neighbour.parent = tile;
      stack.push(neighbour);   // Explore deepest option next
    }
  }
}
⚠ DFS Does NOT Guarantee Shortest Path

DFS may find a path 3× longer than optimal because it doesn't track all shortest distances — it just plunges forward. The visualization clearly shows this: DFS snakes into one corner first before backtracking. Use BFS or Dijkstra when shortest path matters.

Time Complexity: O(V + E) — worst case visits every node.

Space Complexity: O(V) for the stack (worst case a full column of the grid).

Best for: Demonstrating why algorithm choice matters. Maze exploration problems where any path is acceptable.

Dijkstra's Algorithm

Data structure: Priority Queue (min-heap). Implemented here with a sorted array — sort((a,b) => a.distance - b.distance) before each dequeue.

Core idea: At each step, always process the unvisited node with the smallest cumulative distance from start. This greedy minimum-distance selection guarantees the shortest path even with weighted edges.

// Dijkstra core loop (simplified)
const queue = [startTile]; // startTile.distance = 0
while (queue.length) {
  queue.sort((a, b) => a.distance - b.distance); // Always pick minimum
  const tile = queue.shift();
  if (tile.isWall || tile.distance === Infinity) break;
  tile.isTraversed = true;
  traversedTiles.push(tile);
  if (isEqual(tile, endTile)) break;

  for (const neighbour of getUntraversedNeighbours(grid, tile)) {
    if (tile.distance + 1 < neighbour.distance) { // Found shorter path
      dropNeighbourFromQueue(neighbour, queue);   // Remove old entry
      neighbour.distance = tile.distance + 1;
      neighbour.parent = tile;
      queue.push(neighbour);                       // Re-insert with new distance
    }
  }
}
📌 Dijkstra vs BFS on Unweighted Grids

On this grid where every step costs exactly 1, Dijkstra and BFS find identical shortest paths. The difference only emerges with weighted edges. Dijkstra's sort step makes it O(V² log V) here vs O(V+E) for BFS, making BFS strictly faster for unweighted grids. Dijkstra is shown because it demonstrates the general principle that scales to weighted road networks, GPS routing, etc.

Time Complexity (with array sort): O(V² log V) — the sort runs V times.

With a proper priority queue: O((V + E) log V).

A* Search Algorithm

A* is the most sophisticated algorithm in this project. It extends Dijkstra by adding a heuristic — an informed guess about remaining distance — to prioritize nodes that are both close to start AND close to the goal.

The f(n) = g(n) + h(n) formula:

  • g(n) = actual distance traveled from start to node n (same as Dijkstra's distance field)
  • h(n) = heuristic estimate of distance from n to goal (Manhattan distance: |row_n - row_goal| + |col_n - col_goal|)
  • f(n) = total estimated cost — A* always processes the node with the lowest f(n) first
// Heuristic: Manhattan Distance
const retireveheuristicCost = (currentTile, endTile) => {
  const row = Math.abs(currentTile.row - endTile.row);
  const col = Math.abs(currentTile.col - endTile.col);
  return row + col;  // L1 distance — perfect for 4-directional grid
};

// Pre-compute ALL heuristic costs at start
const heuristicCost = initHeuristicCost(grid, endTile); // heuristicCost[r][c]
const functionCost = initFunctionCost(grid);             // f(n) table, init Infinity

// A* core loop
while (unTraversedTiles.length) {
  // Sort by f(n) = g(n) + h(n); break ties by preferring larger g(n)
  unTraversedTiles.sort((a, b) => {
    if (functionCost[a.row][a.col] === functionCost[b.row][b.col]) {
      return b.distance - a.distance; // Prefer closer-to-goal nodes on tie
    }
    return functionCost[a.row][a.col] - functionCost[b.row][b.col];
  });

  const current = unTraversedTiles.shift();
  // ... process neighbours
  for (const neighbour of getUntraversedNeighbours(grid, current)) {
    const tentativeG = current.distance + 1;
    if (tentativeG < neighbour.distance) {
      neighbour.distance = tentativeG;           // Update g(n)
      functionCost[neighbour.row][neighbour.col]
        = tentativeG + heuristicCost[neighbour.row][neighbour.col]; // f = g + h
      neighbour.parent = current;
    }
  }
}
✨ Why A* Is Faster Than Dijkstra

Dijkstra expands uniformly in all directions (it has no idea where the goal is). A* uses the heuristic to "pull" the search towards the goal, dramatically reducing nodes explored. On an open grid, A* often explores less than 30% of the nodes that Dijkstra would. The visualization makes this comparison visually compelling — A* produces a tight, directed search beam vs Dijkstra's disk expansion.

Admissibility condition: A* finds the optimal path only if the heuristic never overestimates the real remaining cost. Manhattan distance on a 4-directional grid is admissible because the real distance can only be ≥ the Manhattan distance (you can never take fewer steps than the Manhattan distance on a grid).

Path Backtracking — Common to All Algorithms

Every algorithm uses the same backtracking loop after termination:

const path = [];
let curr: TileType | null = grid[endTile.row][endTile.col];
if (curr.parent || isEqual(curr, startTile)) {  // Only if reachable
  while (curr != null) {
    path.unshift(curr);  // prepend: builds path start→goal order
    curr = curr.parent;  // follow linked list backwards
  }
}
return { traversedTiles, path };

This works because every algorithm sets neighbour.parent = currentTile when it discovers a better route to a neighbour. The chain of parent pointers from goal back to start is the shortest path.

Chapter 5: Maze Generation Algorithms

Both maze generators are async functions (unlike pathfinding which is synchronous) because they animate their wall-building process step by step rather than running to completion first.

Binary Tree Maze Algorithm

The Binary Tree algorithm creates a maze where every interior "room" (odd-indexed cell) has exactly one open corridor passage going either North or East. This creates a characteristic bias: every maze generated has a clear horizontal corridor at the top and a clear vertical corridor on the right edge.

How It Works — Step by Step

1
Pre-compute walls entirely in memory first

A boolean isWallMap[row][col] is built without touching the DOM. All outer perimeter cells are marked as walls. Even-indexed interior cells become junction pillars (walls by default).

2
Binary tree decision for each odd-indexed room

For each room cell at an odd row AND odd column: randomly choose to carve a passage either East (mark the wall between current and east neighbor as passage → the wall above east neighbor remains) or North (mark wall above current as passage → east wall stays). Edge cases: first row always carves East, last column always carves North.

3
Collect animation steps

Walk the isWallMap, and for every wall cell, push a closure into the steps[] array. Each closure, when executed, calls setWallTile() which sets grid[r][c].isWall = true and updates the DOM element's className.

4
Stream through animation engine

await runFrameAnimation(steps, getRate) plays back these closures at the configured speed. After completion, a CSS buffer sleep waits for keyframe animations to finish, then setIsDisabled(false) unlocks the UI.

// Binary Tree: North/East carving logic
for (let r = 1; r < numRows - 1; r += 2) {      // Odd rows only
  for (let c = 1; c < numCols - 1; c += 2) {    // Odd cols only
    const isFirstRow = r === 1;
    const isLastCol = c === numCols - 2;

    let carveEast: boolean;
    if (isFirstRow) carveEast = true;             // Top row: always East
    else if (isLastCol) carveEast = false;        // Right col: always North
    else carveEast = getRandInt(0, 1) === 1;      // Random elsewhere

    if (carveEast) {
      if (r > 1) isWallMap[r - 1][c] = true;     // North wall stays, east opens
    } else {
      if (c + 1 < numCols - 1) isWallMap[r][c + 1] = true; // East wall stays, north opens
    }
  }
}

Characteristic bias: Every Binary Tree maze has a "highway" row at the top and a "highway" column on the right — these are always open corridors because the edge rooms can only carve one direction.

Recursive Division Maze Algorithm

Recursive Division starts with an empty open grid and recursively divides chambers with walls, leaving one "door" gap in each wall. The result is a maze with long straight corridors and clear rectangular rooms.

How It Works

1
Draw border walls

Trace the four outer edges clockwise (Top → Right → Bottom → Left) adding wall steps for each perimeter cell.

2
Recursively divide the interior

The divide(row, col, height, width) function picks a random wall line (horizontal if height > width, vertical otherwise), picks a random gap cell as the "door", walls everything on that line except the door, then recurses into both sub-chambers.

3
Base case

When a chamber is too small (height < 2 or width < 2), the recursion stops. This guarantees the algorithm always terminates.

function divide(row, col, height, width) {
  if (height < 2 || width < 2) return;  // Base case

  if (height > width) {
    // Horizontal wall line
    const wallRow = row + getRandInt(0, height - 2) * 2 + 1;
    const passageCol = col + getRandInt(0, width - 1) * 2;  // Door gap
    for (let x = 0; x < 2 * width - 1; x++) {
      if (col + x === passageCol) continue;  // Leave the door open
      addWallStep(wallRow, col + x);          // Wall every other cell
    }
    divide(row, col, (wallRow - row + 1) / 2, width);            // Top half
    divide(wallRow + 1, col, height - (wallRow - row + 1)/2, width); // Bottom half
  } else {
    // Vertical wall line (mirror logic)
    ...
  }
}
📌 Key Difference: Recursive Division vs Binary Tree
  • Binary Tree: Works bottom-up (decides passage for each room independently). Creates highly biased mazes with clear diagonal shortcuts.
  • Recursive Division: Works top-down (divides chambers). Creates more balanced, room-like mazes. Slower to animate because Slow/Medium timings were deliberately increased for educational clarity.

Chapter 6: The Animation Engine

The animation system is the most technically sophisticated part of this project. It needed to solve three problems simultaneously: smooth 60fps rendering, zero-lag speed changes mid-animation, and correct background-tab behavior.

runFrameAnimation: Delta-Time Accumulator Engine

The core function in helpers.ts. All animations — pathfinding traversal, path display, wall generation — flow through here.

export function runFrameAnimation(
  steps: (() => void)[],          // Array of DOM mutation callbacks
  targetOrRate: number | (() => number)  // Fixed ms/step OR live rate getter fn
): Promise {
  return new Promise((resolve) => {
    let currentIndex = 0;
    let lastTime: number | null = null;
    let stepAccumulator = 0;       // Fractional step credit across frames
    const isDynamicRate = typeof targetOrRate === "function";

    const stepToNow = (now: number) => {
      const dt = Math.max(0, now - lastTime!);   // Delta time in ms
      lastTime = now;

      // Get current ms-per-step (reads live getter every frame if dynamic)
      const msPerStep = isDynamicRate
        ? (targetOrRate as () => number)()       // Called fresh every frame
        : fixedRateMsPerStep;

      // Accumulate fractional steps from this frame's time budget
      stepAccumulator += dt / msPerStep;

      // Execute all whole steps that fit in this frame's budget
      const targetIndex = Math.min(steps.length, Math.floor(stepAccumulator));
      while (currentIndex < targetIndex) {
        steps[currentIndex]();
        currentIndex++;
      }

      if (currentIndex >= steps.length) complete();
    };

    const frame = (now: number) => {
      stepToNow(now);
      if (!isCompleted) rafId = requestAnimationFrame(frame);
    };

    // Fallback: advances animation even if RAF is throttled (background tab)
    const scheduleFallback = () => {
      fallbackTimer = setTimeout(() => {
        stepToNow(performance.now());
        scheduleFallback();
      }, 30);
    };

    rafId = requestAnimationFrame(frame);
    scheduleFallback();
  });
}

Why Delta-Time Accumulation Instead of Fixed Delays?

The naive approach to animation would be: for each step: await sleep(msPerStep). This breaks in two ways:

  • On a 120Hz monitor, the sleep interval is wrong — setTimeout(cb, 16ms) fires at 16ms even if the monitor refreshed at 8.3ms
  • If speed changes mid-animation, you can't change the sleep duration already scheduled

Delta-time accumulation solves both: each frame, we compute exactly how many steps should have advanced given the actual elapsed real-world milliseconds and the current msPerStep. If a frame took 50ms at 10ms/step, we advance 5 steps. If it took 8ms, we advance 0.8 steps (accumulated fractionally). This produces perfectly smooth, monitor-synchronized animation at any refresh rate.

Live Mid-Animation Speed Switching

The magic that enables instant speed changes without restarting animation:

// In SpeedContext.tsx — the ref updates SYNCHRONOUSLY, before React re-renders
const setSpeed = (newSpeed: SpeedType) => {
  speedRef.current = newSpeed;   // ← Ref mutates instantly, no re-render cycle
  setSpeedState(newSpeed);       // ← React state update (async, triggers re-render)
};

// In Nav.tsx — pass the ref, not the state value
await runMazeAlgo({ ..., speed: speedRef });     // not: speed: speed

// In binaryTree.ts — the rate getter reads the ref fresh every frame
const getRate = () => {
  const s = getSpeed(speed);     // s = speedRef.current (live!)
  return s === 0.5 ? 0.85 : s === 2 ? 2.6 : 1.35;
};
⚡ The Pattern: ref for sync-critical values, state for UI

useState triggers an async re-render — the new value isn't readable by running functions until the next render cycle completes. useRef mutates the .current property synchronously and the updated value is immediately readable by any code that holds a reference to the ref object. By passing speedRef (not speed) to the animation engine, the rate getter reads the live speedRef.current on every single requestAnimationFrame tick. Speed changes take effect in under 16ms.

Why Context Over Prop Drilling

The grid state, algorithm selection, and tile positions are needed in multiple component layers. Without Context, you'd need to pass props through 3-4 component levels. Context gives any component direct access without intermediate "relay" props that those intermediate components don't themselves use.

The isNavigationRunningRef Pattern

Another critical ref pattern: isNavigationRunningRef is a MutableRefObject<boolean> passed from App to Nav and Grid.

// In App.tsx
const isNavigationRunningRef = useRef(false);

// In Nav.tsx — set before animation, clear after
isNavigationRunningRef.current = true;   // Block grid interaction
await runPathAlgorithm(...);             // Animation runs
isNavigationRunningRef.current = false;  // Re-enable interaction

// In Grid.tsx — check on every pointer event
const handleGridMouseDown = (e: React.MouseEvent) => {
  if (isNavigationRunningRef.current) return;  // Block during animation
  ...
};

A ref is used here instead of state because: (1) changing this value does not need to trigger a re-render — we just want Grid's event handlers to know the current status, and (2) refs are synchronously readable from inside async functions like the animation loop, while state updates are asynchronously applied after re-renders.

Chapter 8: Grid & Wall Drawing System

Direct DOM Access Pattern

The grid uses an unusual hybrid: React renders the initial grid, but wall drawing and animation both use direct DOM manipulation via document.getElementById(`${row}-${col}`).

Every tile element's ID is its grid position: id="23-45" for row 23, column 45. This makes O(1) DOM lookup trivial.

Wall Drawing with Linear Interpolation

Fast mouse drags can skip multiple cells in one event. Without interpolation, you'd see gaps in drawn walls.

// Bresenham-style tile interpolation
function interpolateTiles(from, to) {
  const dr = to.row - from.row;
  const dc = to.col - from.col;
  const steps = Math.max(Math.abs(dr), Math.abs(dc));
  const tiles = [];
  for (let i = 1; i <= steps; i++) {
    tiles.push({
      row: Math.round(from.row + (dr * i) / steps),
      col: Math.round(from.col + (dc * i) / steps),
    });
  }
  return tiles;
}

This fills in all grid cells between the last known mouse position and the current one, ensuring smooth wall drawing even at high cursor speeds.

Drag Action Memory

The first cell you click determines whether the entire drag draws walls OR erases them:

// On mousedown — determine drag mode
const el = document.getElementById(`${row}-${col}`);
const isWall = el?.className.includes("bg-gray-300");
dragActionRef.current = isWall ? "normal" : "wall";  // Erase or draw

This prevents accidental mode switches mid-drag if you move over a wall while drawing or vice versa.

DOM → React State Sync on mouseup

During drawing, only DOM elements are mutated (instant). On mouseup, the grid is synced:

const handleGridMouseUp = () => {
  // Read DOM state back into React state
  const newGrid = grid.map(row => row.map(tile => {
    const el = document.getElementById(`${tile.row}-${tile.col}`);
    return { ...tile, isWall: el?.className.includes("bg-gray-300") ?? false };
  }));
  setGrid(newGrid);
};

Chapter 10: Key Engineering Decisions

Decision 1: DOM Mutation Over setState During Animation

🤔 The Alternative (and Why It Fails)

The "React way" would be to call setGrid() on every cell change. On a 47×87 grid with BFS, this means 4,089 setState calls, each triggering a full React re-render of the 4,089-cell grid. At 60fps, that's 245,340 re-renders per second — the browser would hang immediately.

The solution: During animation, bypass React entirely. Mutate the DOM directly and the tile's isTraversed/isWall properties in-place. After animation completes, do one single setGrid() to sync state. This reduces re-renders from 4,089 to 1 per animation run.

Decision 2: Pre-compute Before Animating

Both Binary Tree and BFS/DFS/Dijkstra/A* algorithms run to completion first and produce their full step lists before a single DOM mutation happens. This has two advantages:

  • Separation of concerns: Algorithm logic is pure and testable without any animation side effects
  • Controllable playback: The animation engine gets a complete list of steps it can play at any speed, pause, or even reverse (future feature)

Decision 3: speedRef Bypasses React Re-Render Cycle

See Chapter 7b. The key insight: for values that need to be read synchronously from async animation loops, useRef is correct. useState is for values that should trigger UI updates when they change.

Decision 4: Odd-Dimension Grid for Mazes

// In Nav.tsx — force odd dimensions
if (r % 2 === 0) r += 1;
if (c % 2 === 0) c += 1;

Maze generation algorithms (Binary Tree, Recursive Division) model "rooms" at odd indices and "walls" between rooms at even indices. On a 5×5 grid: rooms are at (1,1), (1,3), (3,1), (3,3); walls between them are at (1,2), (2,1), etc. Even-dimension grids break this model, causing walls to appear at the wrong positions.

Decision 5: Start at (1,1), Goal at (r-2, c-2)

Placing start and goal at these positions ensures they are always inside the first and last "rooms" of any generated maze — the perimeter is always a wall, so the start/goal are never blocked by the outer border.

Decision 6: tailwind-merge for Grid Wrapper

import { twMerge } from "tailwind-merge";
// In Grid.tsx
className={twMerge(
  "inline-flex flex-col ...",
  isNavigationRunningRef.current ? "pointer-events-none" : ""
)}

Tailwind classes can conflict (e.g., pointer-events-auto vs pointer-events-none). twMerge resolves these conflicts intelligently, keeping only the last valid class from each Tailwind group.

Chapter 11: Interview Q&A Bank

Why did you choose to bypass React state during animations? ▼

React's re-render cycle is designed for UI updates that happen at human interaction speeds — button clicks, form inputs, route changes. At animation speeds (60 frames/second across 4,000+ cells), calling setState for every DOM mutation would trigger thousands of full virtual-DOM diffs and re-renders per second. The browser would completely lock up. Instead, I use direct DOM manipulation (element.className = ...) during animation because: (1) DOM mutations via className changes are GPU-composited and hardware-accelerated, (2) bypassing React's VDOM diff eliminates O(N) reconciliation overhead, and (3) CSS animations handle the visual transitions independently after the className is applied. React state is synced exactly once when animation completes via a single setGrid() call.

How does live mid-animation speed switching work without restarting the animation? ▼

The key is using a React useRef instead of useState for the speed value that the animation engine reads. useRef provides a mutable .current property that is immediately readable by any code holding a reference to the ref object — there is no async re-render cycle. When the user changes speed via the SpeedControl component, speedRef.current is updated synchronously. On the very next requestAnimationFrame tick (within ~16ms), the animation engine's rate getter function calls getSpeed(speed) which reads speedRef.current and returns the new ms-per-step value. The delta-time accumulator immediately adjusts how many cells to animate that frame based on the new rate. No restart, no stutter — just a smooth velocity change.

Why is A* better than BFS or Dijkstra on this grid? ▼

BFS and Dijkstra are "blind" — they expand in all directions equally because they have no information about where the goal is. A* uses a heuristic (Manhattan distance: |row_current - row_goal| + |col_current - col_goal|) to estimate the remaining cost to the goal. This biases the search toward the goal direction, dramatically reducing wasted exploration. On an open 47×87 grid, A* might explore 500-1,000 nodes to find a path, while BFS explores 2,000-3,000. The heuristic is admissible (never overestimates) because on a 4-directional grid, you can never reach the goal in fewer steps than the Manhattan distance — so A* is still guaranteed to find the optimal path. The visual difference is striking: BFS shows a circular wave, A* shows a directed beam toward the goal.

What is delta-time accumulation and why is it better than setTimeout? ▼

setTimeout(callback, N) has two problems for animation: (1) it's not synchronized to the monitor's refresh rate, so animations appear choppy at non-60Hz rates; (2) the delay is fixed at call time, so you can't change the speed of an in-flight animation. Delta-time accumulation in requestAnimationFrame solves both. Each frame, I calculate the exact elapsed time since the last frame (dt = now - lastTime), then compute stepsToAdvance = dt / msPerStep. This fractional value accumulates across frames: if a frame took 50ms and msPerStep is 10, we advance 5 steps; if the next frame took 6ms, we advance 0.6 steps (stored as 0.6 in the accumulator). The accumulator means zero wasted time and perfect synchronization with the monitor refresh cycle regardless of whether it's 60Hz, 90Hz, or 120Hz.

Why does the Binary Tree maze always have a clear top row and right column? ▼

It's a fundamental property of the North/East bias carving rule. In the top row (r=1), every room can only carve East (there is no North neighbor inside the grid). In the right column (c = numCols-2), every room can only carve North (there is no East neighbor inside the grid). The result: every room in the top row has an open East corridor connecting it to its East neighbor — forming a continuous horizontal highway. Every room in the right column has an open North corridor — forming a continuous vertical highway on the right edge. This makes Binary Tree mazes trivially easy to solve from top-right to bottom-left but very challenging diagonally. The bias is the tradeoff for the algorithm's O(N) simplicity.

How does wall drawing handle fast mouse movement without gaps? ▼

Mouse events fire discretely — if you drag fast, the cursor may jump from cell (5, 10) to cell (5, 25) in one event. Without handling this, you'd get walls at (5,10) and (5,25) with a gap from (5,11) to (5,24). I solve this with a Bresenham-style linear interpolation function: given the last tile position and the current tile position, it computes all intermediate grid positions along the straight line between them and draws walls at each. The algorithm divides the path into steps = max(|ΔRow|, |ΔCol|) segments and places a wall at each interpolated integer position. This fills every cell even at maximum drag speed.

Why do mazes require odd grid dimensions? ▼

Both Binary Tree and Recursive Division model the maze as rooms at odd-indexed cells and walls/corridors at even-indexed cells. For example, on a 5×5 grid: rooms exist at positions (1,1), (1,3), (3,1), (3,3). The cells at (1,2), (2,1) etc. are "walls between rooms." This two-index grid model requires that the border perimeter is at even indices (0, numRows-1, 0, numCols-1) and the last interior room is at (numRows-2, numCols-2). If numRows is even, the math breaks: the last room and border overlap, causing incorrect wall placement. By enforcing odd dimensions, the grid always has a clean room-wall-room-wall-room pattern from edge to edge.

What is the time complexity of A* in this implementation? ▼

In this implementation, A* uses a plain array sorted before each dequeue: O(V log V) per sort operation, running up to V times, giving O(V² log V) total. For a 47×87 grid (4,089 cells), this is ~4,089² × ~12 ≈ 200 million operations in the theoretical worst case. In practice, A* terminates much earlier because the heuristic prunes most of the search space. A production-grade A* would use a binary min-heap priority queue (O(log V) insert/extract) for O((V + E) log V) total. For this grid size, the array sort approach is acceptable and the code is simpler to read and explain in interviews.

How does Recursive Division guarantee the maze is always solvable? ▼

Every wall line drawn by Recursive Division has exactly one "door" gap — a cell that is deliberately left open. This gap connects the two sub-chambers separated by that wall. Since every chamber division preserves at least one passage, and the algorithm recurses until chambers are too small to divide further, every part of the interior remains connected to every other part through the chain of passage gaps. The perimeter border has no gap (it forms the outer walls), but the start and goal are placed at (1,1) and (r-2, c-2) — always inside the first and last rooms — so they are always reachable through the interior passage network.

Walk me through what happens when I click "▶️ Start" on BFS. ▼

1. handlerRunVisualizer() in Nav.tsx sets isDisabled = true and isNavigationRunningRef.current = true, blocking grid interaction.

2. All tile states (isTraversed, isPath, parent, distance) are reset on the grid object in-memory.

3. runPathAlgorithm({ algorithm: "BFS", grid, startTile, endTile, speed: speedRef }) is called.

4. Inside, bfs(grid, startTile, endTile) runs synchronously — it uses a FIFO queue, sets parent pointers and distance values, and returns { traversedTiles, path }. This runs in milliseconds regardless of grid size.

5. animatePath(traversedTiles, path, startTile, endTile, speedRef) is called. It builds step closures for every tile in traversedTiles and path.

6. runFrameAnimation(traversalSteps, getTraversalRate) plays the traversal: each frame, it reads speedRef.current via getTraversalRate(), computes how many cells to animate using delta-time, and mutates their DOM className to add animate-traversed (or -fast/-slow variant).

7. After traversal, a short pause, then runFrameAnimation(pathSteps, getPathRate) replays the optimal path in green.

8. Once both Promises resolve, setGrid() syncs DOM state into React, setIsGraphVisualized(true) changes the Start button to "Reset", and setIsDisabled(false) re-enables interaction.
